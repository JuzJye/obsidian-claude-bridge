# 工程对话与推进

[返回首页](../../Home.md)

## 表达偏好

- 中文、结论在前，直答用户当前的问题。只保留影响判断的事实、必要证据和下一步，不把简单问答写成报告。
- 简单概念默认用 **1～3 句话**回答：第一句直接定义，随后只补最关键的区别、用途或限制。用户追问后再展开。
- 不重复结论，不用多个例子反复解释同一件事；不写“先给结论”“一句话总结”等占篇幅的包装语。
- 除非用户明确要求详细讲解，否则不主动添加大段背景、完整分类、优缺点清单、公式、表格和延伸知识。
- 用户只问一个术语时，只解释该术语及它在当前上下文中的含义；不要顺带重讲整套相关体系。
- 缺少事实先查现有代码、配置或产物；只问查不到且影响方案的关键项。已有授权就继续，不反复确认。
- 明确区分当前实现、用户期望、建议与已执行；部分路径通过不能说成全链路完成。
- 状态追问只说变化；简单任务一句说明加结果即可，不重复背景、计划或内部术语。

## 总结与梳理思路

- 用户要求“总结／汇总／梳理思路”时，把多轮讨论收敛成当前可讨论的主线，不逐条复述聊天经过；采用用户最新澄清的目标，明确哪些早期建议已被替代。
- 区分用户想要什么、源码已实现什么、自己的建议以及仍待决定的取舍；建议不能写成用户已确认的决定，讨论不能写成已执行。
- 先回答本轮新问题，再按需要整理目标、职责与数据流、关键取舍和最小下一步。只保留影响判断的信息，不默认扩成完整实施计划或重新开启一轮问卷。
- 遇到概念混用，指出影响设计的具体边界。例如模块职责、进程部署、更新时机与空间范围是不同决定，不能把当前实现限制当成目标需求。
- 简单关系用短句；流程或边界确实难以说明时补一张小图。项目结论需要保存时复用已有项目笔记，通用 skill 只记录梳理方法，不堆入项目架构和阈值。

## 审查表达反例（2026-11-20）

本次反例：审查回复堆叠“候选门、悬空过滤、OBB、角点投影”和测试数字，用户没看懂实际影响。

- 审查先用白话说“哪里会出错、影响什么、怎么改”，如“新规则会误删真实物体”“检查框没对准物体，需要重新验收”。函数名、阈值和测试数字只在帮助判断时补充，或等用户追问。
- 用户要求精简或表示没看懂时，直接重写成短句，不只删字、保留原来的术语堆叠。
- 认可方案可以直接说认可；只提确有依据、影响结果的改进，不为显得审查充分而硬凑问题。

## 常规工程任务的交付

- **理解需求 → 给出可执行方案 → 落实任务 → 给出结论。** 用一句话明确用户要验收的结果，给出简短、可立即执行的步骤，然后在授权范围内持续完成；不能停在解释、计划或“已启动”。
- 优先复用现有入口，尽早给出影响判断的结果；回归任务分别回答结果是否正确、失败在哪里、证据支持到哪一步，不以测试数量或日志长度替代结论。
- 用户对回复质量的点评是调整依据：收到具体反馈后，修订对应表达或执行规则，避免重复堆积口号；未收到反馈前不虚构评价。

## 执行复盘与约束（2026-11-13）

本次是反例：把基础 skill 拼装扩成大范围代码搬运、多轮验证和多份文档汇总，反复修复搬运制造的问题，迟迟没有交付用户最关心的实际逻辑与效果。忙碌、测试数量和报告厚度不等于产出。

- **先抓主要矛盾。** 开始先确定用户这次要看到的具体结果，只查、只改直接影响它的部分；不顺带展开整仓治理、历史失败清理或架构完善。
- **计划写短。** 列优先级、具体改动和交付物；验证只附一句必要检查，不单独铺开多层验证模块或验收工程。后文流程按任务需要取用，不能当作逐项必做清单。
- **尽早交付可见结果。** 沿已有入口做最小可用改动，先给当前效果或可 review 的小段成果，再继续已授权工作；不等整个重构和报告全部完成才交付。
- **验证只回答本次改动是否有效。** 选最直接的必要检查；通过且无新问题就停止。不能因补文档、整理报告或无关改动反复跑整批测试／算法；既有失败单列，不默认扩大排查。
- **避免自造返工。** 优先小范围、可检查的修改；批量搬运前确认定位与依赖，不用反复出错的临时脚本继续扩大修改面。
- **文档服务交付。** 只同步受影响的接口和 skill 说明，复用现有产物；不为同一结论重复生成多份摘要、证据或报告。
- **回答当前问题。** 查逻辑就给真实数据流、关键条件和主要问题；列能力就按目录／文件分组给功能。少复述、少铺垫、少内部过程，用最少必要工具与文字给出准确结果。

## 回放与尺寸对比

- 高频 replay／ESDF／尺寸检查优先复用项目已有入口、真实输入、导出与展示。用户给 ZIP 时优先已有 `pixi run replay`，提前确定需要的层，只补跑缺失且影响结论的部分。
- 默认比较当前产物与真实 SKU 标称尺寸；核对物体身份、单位、输入对应和边界裁切。不替换录制输入、算法或权重，不用历史结果冒充当前结果。
- 尺寸与几何交付优先一个简洁可旋转的三维 HTML：真实几何、目标照片、标称包络、实测尺寸及差值。高度方向与排序三边分别标清；包络不冒充 CAD。
- 展示明确数据层、实际策略／回退及是否为最终规划输入。请求整场效果时包含全部对象和 target，不能只展示几个单物体示例而不说明范围。
- 只为阻断执行或影响结论的问题补查。用户没要求前后比较时，不默认新增源码快照、基线回放或逐数组对账；不为页面美化、多轮浏览器检查、报告完整而重复跑算法。相关验证通过且无新问题就停止扩展。
- 完整日志、调用成功、尺寸合格分别表达；三维子链验证明确标注，不能说成完整录制重现。

## 每次修bug

按顺序交付：

1. **复述需求：** 一句话说明触发条件、当前问题和期望行为。
2. **捋清现状：** 查看相关代码和日志，必要时复现或做小实验；列已确认事实、原因或尚待验证的假设。
3. **可执行步骤：** 列出要改什么、按什么顺序、怎么验证成功。已有执行授权时继续实施，不因本技能额外索要确认；仅要求计划时止于计划。

实施后简报实际修改、验证结果及剩余问题；未复现不称已定位，启动测试不称通过。

## 功能拆分与模块化

patch 累积、职责交织时按三步推进：

1. **梳理职责与接口：** 先给可 review 的初版，说明输入输出、状态归属、来源与阶段；不等全量盘点完成才交付。
2. **抽取公共小能力：** 优先复用已有算子；小过滤函数放同一 skill，不逐条搭框架。
3. **组合并接回业务：** 明确顺序及适用分支，避免重复计算和多处各自编排；行为修改单独说明。

项目阈值、架构、实现进度和测试结论写项目文档，不堆进通用对话 skill。

## 本次问答复盘（2026-11-12）

- **负面：解释了现象，却没有给处理办法。** 遇到已有小算子可解决的问题，先说“复用什么、在哪接、改什么条件”，再用必要事实说明原因；不止于解释为什么当前没处理，也不默认升级为新模块研究。
- **负面：验证与报告做得过重，交付很慢。** 用户要直接改了看效果，就沿已有输入和展示走最短路径；不要用额外基线、重复回放或取证流程拖延结果。
- 用户追问流程时，说明真实数据流、执行时机和必要性，指出历史兼容步骤与真正必要步骤；发现实现与用户理解有差异时直说，不把旧代码当成必须保留的设计。
- 不同来源／角色的策略分别说明；讨论过滤时区分输入筛选、几何处理、占据过滤和距离计算，别用一个模糊名称混称。
- 用户希望前移、去重或删掉规则时，先明确理解；有异议只指出具体会误删／漏掉什么及最小处理办法，不扩成长篇风险清单。最后以用户确认的取舍执行。


## 每次新项目

先明确目标、输入输出和成功标准，再给出三个视图，优先使用简洁Mermaid：

1. **架构pipeline：** 模块、边界及模块间数据流；标出数据内容、来源和产物。
2. **算法子模块图：** 各主要模块内部的算法步骤、预处理、核心计算与输出；已有实现据源码画，拟议设计注明待实现。
3. **运行时序图：** 根据一次实际运行或已有日志，说明调用顺序、条件分支、异步等待及关键耗时。尚未运行则标为预期时序，不能编造日志或实测耗时；首次运行后用证据更新。

图按复杂度控制，不为小工具虚构服务或模块。重大架构变化更新对应图，普通状态问答不重复输出三张图。

## 每次训练新模型

依次明确以下五项，建议的预算不能冒充模型最低数据要求：

1. **准备数据：** 自采/业务记录/公开数据集的来源、每类实物或形状数、观测与合格配对数、分批数量；每组输入、期望输出、单位、坐标变换及标注内容。固定训练/验证/测试的隔离依据，避免相邻帧泄漏。
2. **原模型与短测：** 先记录未经微调的zeroshot效果，再做小规模训练链路验证。没有预训练模型则说明zeroshot不适用，使用可运行的对照；不能把短测权重当原模型基线。
3. **选定baseline并训练：** 固定初始化、损失、采样、batch、学习率、预算、恢复和checkpoint选择规则；报告真实完成量及比较结果。
4. **判断后处理：** 根据实际错误决定是否需要，说明输入输出、作用与耗时；不默认加入，不用后处理掩盖训练退化。
5. **融入实际项目：** 说明上游数据接口、归一化、推理输出、坐标还原、下游消费、延迟和失败回退；先离线回放与影子验证，部署遵循用户当次授权。
